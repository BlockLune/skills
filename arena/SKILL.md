# Arena

## 1. 定义任务

明确交付物、约束和共享上下文，形成所有候选共用的任务说明。另行制定 3–6 项可逐项评分的评审标准；候选只接收任务说明，评审阶段再使用评分表。

用户未指定数量时，默认生成 3 个候选。按当前环境可用的模型和子代理能力分配：判断或设计任务优先使用不同模型，生成任务可以使用同一模型的独立实例。无需固定模型或工具；无法并行时，先说明限制，与用户确认替代方式。

每个候选使用独立的工作目录：代码优先使用 git worktree，其他产物可使用临时目录。确保它们从同一份任务上下文和代码快照出发，包含任务所需的未提交修改，彼此隔离写入。

## 2. 并行生成

同时启动全部候选，提供相同的任务说明、共享上下文位置和各自的输出位置。要求每个候选交付产物，以及简短的取舍说明：考虑了哪些方案、为何选择当前方案、放弃了什么。

候选独立完成，期间互不读取结果。某个候选失败时，记录退出原因，继续评审剩余候选；若不足两个候选，补充候选或与用户确认改为单方案交付。

## 3. 独立评审与选优

所有候选停止写入后，启动一个只读评审代理，优先选择与主代理不同的模型系列。提供评审标准和按中性标签标识的候选路径，要求逐项评分并推荐基底。若没有独立评审能力，在综合记录中注明。

主代理与评审代理并行工作：完整阅读每个候选，按同一标准逐项评分，再对照评审意见。出现分歧时，核查双方理由与产物证据；标准含糊时先澄清标准，再作选择。

选出最便于后续维护、扩展且能守住关键约束的基底。评分接近时，优先选择边界更清晰、接口更小的方案，记录选择理由及独立评审结论。

## 4. 融合

重新检查每个落选候选，将确有价值的部分按基底的整体设计重新整合。逐项记录来源、采纳内容，以及未采纳的重要思路和理由。

候选趋同时，可以直接采用共识方案，无需强行融合。若分歧源于对任务的不同理解，回到任务定义，澄清后重跑，而非折中拼接；合理的设计分歧则按评审标准取舍。

## 5. 验证与交付

验证融合后的最终产物，而非沿用候选的验证结论。代码运行相关测试和检查；文档、设计等交付物逐项核对任务约束、事实依据和内部一致性。记录实际执行的验证、结果及尚未验证的部分。

验证失败时追溯原因：任务定义有误则重新定义并生成候选，遗漏候选优点则返回融合，融合引入的问题则修正后重新验证。

交付最终产物，并在旁边保存一份简短的综合记录，包含：

- 各候选的逐项评分、基底选择理由和独立评审结论。
- 融合内容及来源、重要舍弃项及理由。
- 候选退出、能力限制和验证结果。
