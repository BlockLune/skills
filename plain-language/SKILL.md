# 简明写作

按 80% 的 `ASD-STE100`、`ISO 24495-1:2023 Plain language` 与 `BLUF / Minto / Diátaxis` 写作或改写。直接输出正文，不写寒暄、动作预告、指向文档自身的话（“本文/本节/下表/综上所述/值得注意的是”）、事后修改总结或规则声明。

## 结构与保真

- 结论先行与金字塔组织（BLUF / Minto）：首段给核心结论，段首第一句点题，同层并列项归为同类，不在读者需要前堆砌背景；同一事实全文只写一次。
- 独立成篇与全文对账：开头交代适用范围与前提，首次出现的领域概念给定义，不要出现元描述，比如“如刚才讨论”这类对话指代、“下面说明...”这类行文思路等；对照真实执行记录、源码或原文核对数字与结论，单列未覆盖、未验证和待决事项。
- 按用途分流：技术文档按 Diátaxis 区分教程、操作指南、参考与解释，操作步骤里不塞大段背景解释；Commit 与 PR 描述先写问题与影响，再写为什么改，不复述代码字面改动。
- 保真与限定词：不因追求简短而删减事实、数字、前置条件、异常分支或代码示例（改写后可以比原文长）；保留“可能/通常/至少/尽快/大多数”等限定词，不改变原有的确定程度（不把“可能”改成“是”或把“尽快”改成“立即”）；信息缺失时追问或标明未知。

## 中文写法

- 直接用动词（写“清洗数据”，不用“进行/加以/作出/予以 + 动词”）；操作步骤用编号列表、动词开头，不写“请/您/用户需要”。
- 数字带单位，范围写清端点（写“大于 10 / 不小于 10”，不用含糊的“10 以上/以下”）；同一概念全文固定一词，“它/这/该”有歧义时换回具体名词。
- 清理套话（保留正当例外）：
  - 不用空洞的“不是 A 而是 B / A 不重要，重要的是 B”（纠正真实误解、做技术对照或表达“不只 A 还 B”除外）。
  - 不为了凑结构硬套“首先…其次…最后…”或强凑三个排比词（客观上恰好是三个真实步骤或并列项除外）。
  - 段末写完事实即停，不写“这说明/由此可见/这体现了……”等拔高句；将“赋能/抓手/闭环/打法”换成具体动作，“发现 N 个失效项”直接写“N 个失效项”。

## 英文写法

- 不用空洞的 `It's not just X; it's Y` 或 `Not because X. Because Y.`（真实纠偏与技术对照除外）；不写 `Here's the thing:`、`Let's dive in`、`That is the real win.`、`Let that sink in.` 等开场与收尾套话。
- 不在句末挂 `, highlighting / underscoring / showcasing...` 等拔高分词，改用 `to <verb>` 或独立句子写具体作用。
- 不用分号（`;`）串联句子，不用破折号（`—`）堆叠插入语，改用句号拆成独立短句。

## Markdown 版式与工具

- 标题从单个 `#` 连续递增，优先使用一至三级，不建议四级，禁止五级及以上；中文与英文、数字、版本号之间加空格（例如 `使用 React 19 构建应用`）。
- 并列项用 `-`，连续步骤用 `1.`；表格用于对比或紧凑数据，段落或列表更易读时优先用它们，两列键值信息用 `- a: b` 列表；围栏代码块标注语言，图片配说明性 alt 文本。
- 修订时保留原有粗体、斜体风格；新建文档克制使用加粗和斜体（不要把列表项开头都加粗），尽量使用普通文本。
- 需要改写对照示例时读取 [EXAMPLES.md](references/EXAMPLES.md)；有字数限制或需运行 `rumdl`、`autocorrect`、`pangu` 检查时读取 [TOOLS.md](references/TOOLS.md)。
