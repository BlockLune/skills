# 事实归属、触发清单与计划文件

## 事实归属与冲突规则

按照“这份内容会因为什么而变化”划分文档归属，变化原因不同的内容拆分到不同文件。只在归属文件里记录事实，其他文档只放置链接：

- 系统行为：写入规格文档（例如 `docs/spec.md`）。规格文档只记录当前状态。
- 实现状态：写入一张状态表。
- 外部系统的行为与验证状态：写入接口契约文档。
- 架构决策与原因：写入 ADR（例如 `docs/adr/`）。
- 领域术语：写入术语表，只收录代码里看不出来的领域词汇；仓库已有术语文件时沿用原有的文件名。
- 待实现计划、候选方案与实现前要确认的事项：写入独立的计划文件（例如 `docs/plans/`，一项功能一个文件），功能实现后删除。

两处说法不一致时，以归属文件为准，再修改引用该文件的其他位置。

## 触发清单

触发清单是一张“修改了哪里 → 在同一个提交里核对哪些文档”的对照表。已有仓库按照实际存在的文档填写；新建仓库先放置 3 到 4 行通用触发项，并在表格后注明“再次出现文档与代码不一致时补充一行”。每一行只指向已经存在的文件：右列的文档还不存在时暂不写入这一行，等待文档建立后再补充，不为凑齐清单新建空白文档。通用触发项：

| 修改范围 | 核对文档 |
| --- | --- |
| 用户可见的界面或行为 | 对应的规格文档 |
| 对外接口或上游契约 | 接口契约文档 |
| 依赖或构建 | 构建说明与 `README.md` |
| 一项功能完成 | 实现状态表；删除 `docs/plans/` 下对应的计划文件 |

## 计划文件兼作交接文件

计划文件包含四节：已完成、已确认、待处理、下一步。新的会话直接读取计划文件继续执行，无需另外建立状态恢复机制。
