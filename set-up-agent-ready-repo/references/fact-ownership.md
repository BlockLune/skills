# 内容分工、ADR 规则、文档更新清单与计划文件

## 内容分工与存放位置

优先把信息放在离代码最近、最容易自动检查的地方。能用代码、类型、测试或 lint 说清的，不另建文档；规格文档、接口契约、术语表与 ADR 全部按需建立，不为凑齐目录新建空白文件。

按以下优先级决定放哪里。同一内容只记在主文档里，其他地方只放链接：

| 内容类型 | 存放位置 | 适用判断 |
| --- | --- | --- |
| 当前做了什么 | 代码本身 | 默认来源，不另写文字复述实现 |
| 必须遵守的约束 | 类型、测试、lint、权限规则或 hook | 能自动检查的先写成可执行检查 |
| 局部的“为什么” | 就近代码注释 | 只影响单个函数或文件（如 workaround、反直觉写法、性能取舍），删代码时一起消失 |
| 单次改动的过程与背景 | Commit message 或 PR 描述 | 一次性上下文、改动动机与评审讨论 |
| 待实现方案、候选方案、待确认项与交接状态 | 独立计划文件（如 `docs/plans/`，一项功能一个文件） | 实现后删除，不长期保留 |
| 系统行为、实现状态、外部接口契约或领域词汇 | 规格文档（如 `docs/spec.md`）、状态表、接口契约或术语表 | 按需建立，只记代码看不出来的当前状态、外部系统行为与验证状态或领域边界，不写历史流水账 |
| 跨模块或难逆转的取舍理由 | ADR（如 `docs/adr/`） | 满足下方准入门槛时才写 |

变化原因不同的内容拆到不同文件。仓库已有同类文档时，沿用原有文件名和路径。

### 冲突处理

- 文档互相引用出现不一致时：以主文档为准，更新引用方。
- 代码与 ADR 或规格文档不一致时：不能自动以任何一方为准。先停下来由人判断是实现出错还是决策已变，再修代码或更新对应文档。

## ADR 准入与维护

### 什么时候写 ADR

同时满足以下两条才写 ADR：

- 去掉背景后，一个有能力的维护者或 agent 很可能会把它改成另一种“看起来更合理、实际会踩坑”的做法。
- 影响超出单个模块，或涉及外部约束、长期数据或接口兼容、难逆转的边界，光靠代码注释或测试说不清。

普通实现细节、常规重构和单次方案讨论不写 ADR。agent 在普通开发任务中不擅自新建 ADR；遇到满足门槛的决策时向用户提议，确认后再写入。

### 写法与生命周期

- 一篇只记一个决定，写短、写具体，包含：状态、背景、决定、被否决的方案与原因、接受的代价，以及关联的代码或检查路径。
- 尽量配一条类型、测试或 lint 守住这个决定。检查负责拦住违规改动，ADR 负责解释为什么这算错，避免后续 agent 为完成任务把检查改掉。
- 在 `docs/adr/` 下维护简短索引，标明状态与适用模块。修改对应模块时按需读取，不在入口文件加载全部 ADR。
- 决策变更时，新建 ADR 替代旧 ADR，并在同一次提交里完成三件事：在旧 ADR 文件头标明 `Status: Superseded by ADR-xxx`、把旧 ADR 移入 `docs/adr/archive/`、更新索引。默认搜索和入口索引只看当前生效的 ADR，不读 `archive/`。

## 文档更新清单

文档更新清单记录“改了哪类代码 → 在同一次提交里核对哪份文档”。已有仓库按实际存在的文档填写；新建仓库按需从中挑 3 到 4 行，并在表后注明“再次出现文档与代码不一致时补充一行”。

只写指向已有文件的行。右列文档还不存在时暂不写入，等文档建好后再补。常用项：

| 修改范围 | 核对文档 |
| --- | --- |
| 用户可见的界面或行为 | 对应的规格文档 |
| 对外接口或上游契约 | 接口契约文档 |
| 依赖或构建 | 构建说明与 `README.md` |
| 一项功能完成 | 实现状态表；删除 `docs/plans/` 下对应的计划文件 |
| 推翻原有架构决策 | 新建 ADR，将旧 ADR 归档到 `docs/adr/archive/` 并更新索引 |

## 计划文件兼作交接文件

计划文件包含四节：已完成、已确认、待处理、下一步。新会话直接读计划文件继续工作，不用另建状态恢复机制。
